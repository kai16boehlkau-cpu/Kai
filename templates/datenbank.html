Datenbank

Wo deine Einträge wirklich liegen

Wenn du ein Lebensmittel speicherst, verschwindet es nicht „irgendwo im Programm“, sondern in einer Datei namens database.db – eine - Datenbank direkt neben app.py. Auf dieser Seite steht, was darin gespeichert ist, wie der Python-Code damit arbeitet und warum manche Spalten so gebaut sind, wie sie gebaut sind.

KAPITEL 01

Was ist eine Datenbank überhaupt?

Die Grundidee in zwei Minuten erklärt.

Stell dir eine Tabellenkalkulation vor, bei der du nicht aufpassen musst, dass jemand eine Zeile verschiebt oder eine Formel überschreibt: So ungefähr arbeitet eine Datenbank. Die Daten liegen in Tabellen aus Zeilen (ein Eintrag pro Zeile) und Spalten (ein Merkmal pro Spalte, z. B. „Name“ oder „Kalorien“). Jede Spalte hat einen festen – SQLite weist eine Zeile ab, in der in der Kalorienspalte plötzlich Text steht. Genau diese Festigkeit ist der Vorteil gegenüber einer einfachen Textdatei.

Datei statt Server

Alles in einer Datei

SQLite braucht keinen eigenen Datenbank-Server. Die ganze Datenbank ist die eine Datei database.db. Zum „Sichern“ dieser App kopiert man also im Zweifel einfach diese eine Datei.

Bereits enthalten

In Python eingebaut

Das Modul sqlite3 gehört zur Python-Standardausstattung. Für das Projekt muss deshalb nichts installiert oder konfiguriert werden – import sqlite3 genügt.

Genau richtig

Für ein Schulprojekt ideal

Eine App mit einer Person und ein paar hundert Einträgen braucht keine große MySQL-Installation. SQLite schafft problemlos mehrere hunderttausend Zeilen und ist trotzdem so simpel wie eine Datei.

KAPITEL 02

Die zwei Tabellen im Detail

Die Datenbank hat genau zwei Tabellen: entries für Mahlzeiten und settings für das Tagesziel. Klicke eine Spalte an, um Beispielwert und Hintergrund zu sehen.

Aufbau von database.db
Primärschlüssel (PK) Die Spalte id: jede Zeile bekommt ihre eigene, eindeutige Nummer. Damit findet das Programm später genau diese Zeile wieder – auch wenn der Name zweimal vorkommt.
TEXT Text. Wird hier für Namen (Apfel) und Datumsangaben (2026-10-22) benutzt.
REAL Eine Zahl mit Nachkommastellen, z. B. 379.5 Kalorien pro 100 g oder 150.5 Gramm als portionsweise Menge.
INTEGER Eine ganze Zahl ohne Nachkomma, z. B. die 227 Kalorien einer Portion oder das Tagesziel 2000.
entries – jede Mahlzeit ist eine Zeile
  • id INTEGER PK +
    Eindeutige Nummer der Zeile. Über sie wird ein Eintrag später geändert oder gelöscht.
    Beispiel 4

    Die Nummern vergibt SQLite selbst (AUTOINCREMENT): jede neue Zeile bekommt die nächste freie Nummer, doppelte IDs sind unmöglich.

  • name TEXT +
    Was gegessen wurde, z. B. „Haferflocken mit Milch“ (höchstens 80 Zeichen).
    Beispiel Haferflocken mit Milch

    Der Name wird frei getippt. NOT NULL sorgt dafür, dass keine leere Zeile gespeichert werden kann – die Prüfung passiert vorher in Python.

  • calories_per_100g REAL +
    Der Kalorienwert pro 100 g, den du eingetragen hast – z. B. 379.5.
    Beispiel 379.5

    REAL statt INTEGER, weil Nährwertangaben oft Nachkommastellen haben. Erlaubt sind Werte von 1 bis 900 – mehr hat kaum ein Lebensmittel.

  • amount_grams REAL +
    Wie viel gegessen wurde, z. B. 60 Gramm.
    Beispiel 60

    Auch 2.5 Gramm für Gewürze ist möglich, deshalb REAL. Python akzeptiert übrigens auch 2,5 mit Komma und wandelt es um.

  • calories INTEGER +
    Kalorien der Portion, in Python berechnet: 379.5 × 60 / 100 = 228. Wird mitgespeichert, damit die Tagesumschau schnell addieren kann.
    Beispiel 228

    INTEGER, weil für die Anzeige ganze Kalorien reichen – round() rundet. Der Wert wird beim Speichern berechnet und dann nie mehr geändert.

  • meal TEXT +
    Eine von vier Mahlzeiten: Frühstück, Mittagessen, Abendessen oder Snack.
    Beispiel Frühstück

    Erlaubt sind nur die vier Werte aus der Liste MEALS in app.py. validate_entry_form() prüft das vor dem Speichern.

  • date TEXT +
    Der Tag der Mahlzeit im Format JJJJ-MM-TT, z. B. 2026-10-22.
    Beispiel 2026-10-22

    Dieses Datum steht auch in der Adresszeile (/?date=2026-10-22). Dashboard und Kalender filtern genau mit dieser Spalte.

  • created_at TEXT +
    Uhrzeit des Speicherns, z. B. 16:41:07. Damit bleibt die Reihenfolge der Einträge eines Tages erhalten.
    Beispiel 07:12:44

    datetime.now() schreibt die Uhrzeit beim Speichern. ORDER BY created_at zeigt morgens zuerst das Frühstück – auch ohne die Mahlzeit-Spalte.

↔ getrennt gespeichert Das Tagesziel hat mit Mahlzeiten nichts zu tun – deshalb steht es nicht als Spalte in entries, sondern in der eigenen Tabelle settings.
settings – immer genau eine Zeile
  • id INTEGER PK +
    Immer 1 – es gibt nur diese eine Zeile in der ganzen Tabelle.
    Beispiel 1

    Der Wert ist fest verdrahtet: alle Abfragen und Updates nutzen WHERE id = 1. Eine zweite Zeile gibt es konstruktiv nicht.

  • daily_goal INTEGER +
    Das Tagesziel in kcal, z. B. 2200.
    Beispiel 2200

    Änderbar ist das Ziel nur über die Einstellungsseite. Erlaubt sind 800 bis 6000 – auch diese Prüfung passiert in Python vor dem Speichern.

  • goal_set INTEGER +
    1 heißt: das Ziel wurde selbst gespeichert. 0: es steht noch der Standardwert. So erkennt die App, ob das Start-Formular nötig ist.
    Beispiel 1

    Eigentlich bräuchte man nur die Zahl 0/1: Die App prüft mit goal_is_set(), ob das Einrichtungs-Formular angezeigt werden muss.

KAPITEL 03

Ein Eintrag – Schritt für Schritt

Was passiert, sobald du auf „Speichern“ klickst? Alle Codebeispiele sind Ausschnitte aus app.py.

1

Der Browser schickt das Formular an den Server

Das Formular auf dem Dashboard hat method="POST" und geht an die Adresse /add_entry. leitet diese Anfrage an die Python-Funktion add_entry() weiter.

2

Python prüft jede Eingabe, bevor etwas gespeichert wird

Was im Browser eingegeben wurde, kann alles Mögliche enthalten – auch Unsinn. Deshalb prüft validate_entry_form() jeden Wert einzeln und meldet verständliche Fehler statt späterer Datenbank-Chaos-Meldungen:

app.py – validate_entry_form() Python 
if name == "":
    return {"error": "Bitte gib einen Namen für das Lebensmittel ein."}
if calories_per_100g <= 0 or calories_per_100g > 900:
    return {"error": "Kalorien pro 100 g müssen zwischen 1 und 900 liegen."}
if meal not in MEALS:
    return {"error": "Bitte wähle eine gültige Mahlzeit aus."}
3

Die Kalorien der Portion werden berechnet

Der Wert pro 100 g allein sagt wenig – interessant ist die tatsächliche Portion. Die Rechnung läuft in Python und wird als fertige Zahl mit in die Datenbank geschrieben:

app.py – calculate_calories() Python 
# Kalorien = Kalorien pro 100 g x Gramm / 100
# Beispiel: 379.5 x 60 / 100 = 227.7 -> auf 228 gerundet
return round(calories_per_100g * amount_grams / 100)
4

Der Eintrag geht per INSERT in die Tabelle

Jetzt schreibt SQLite die Zeile. Auffällig sind die ?- : Der SQL-Text und die Werte werden getrennt übergeben (mehr dazu in Kapitel 04). speichert die Änderung dauerhaft in der Datei.

app.py – add_entry() Python + SQL 
connection.execute(
    """
    INSERT INTO entries
        (name, calories_per_100g, amount_grams, calories, meal, date, created_at)
    VALUES (?, ?, ?, ?, ?, ?, ?)
    """,
    ("Haferflocken mit Milch", 379.5, 60, 228,
     "Frühstück", "2026-10-22", "07:12:44"),
)
connection.commit()  # erst hier ist die Zeile wirklich gespeichert
5

Die Seite liest den Tag mit SELECT wieder aus

Nach dem Speichern leitet Flask zurück zum Dashboard. Dort holt index() alle Einträge des gewählten Tages aus der Tabelle – wieder mit Platzhalter für das Datum – und addiert zusätzlich die Kalorien direkt in SQL:

app.py – index() Python + SQL 
rows = connection.execute(
    "SELECT * FROM entries WHERE date = ? ORDER BY created_at",
    (selected_date,),   # z.B. "2026-10-22"
).fetchall()

# SUM addiert alle Kalorien des Tages, COUNT zählt die Einträge
stats = connection.execute(
    "SELECT COALESCE(SUM(calories), 0) AS total, COUNT(*) AS count "
    "FROM entries WHERE date = ?",
    (selected_date,),
).fetchone()
KAPITEL 04

Ändern, Löschen, Tagesziel speichern

Es gibt vier SQL-Befehle, die in dieser App gebraucht werden: SELECT, INSERT, UPDATE und DELETE.

01

UPDATE – einen Eintrag überarbeiten

Wird im Formular etwas geändert, ruft die App /update_entry/<id> auf. Die id der Zeile ist dabei der Anker: Ohne sie müsste man raten, welche der mehreren „Apfel“-Zeilen gemeint ist.

app.py – update_entry() Python + SQL 
connection.execute(
    """
    UPDATE entries
    SET name = ?, calories_per_100g = ?, amount_grams = ?,
        calories = ?, meal = ?, date = ?
    WHERE id = ?
    """,
    ("Apfel", 52.0, 150, 78,
     "Snack", "2026-10-22", 5),   # 5 = die alte id bleibt erhalten
)
02

DELETE – einen Eintrag entfernen

Löschen geht mit einer einzigen Zeile. Auch hier entscheidet wieder die id, welche Zeile gelöscht wird – alle anderen Zeilen bleiben unangetastet.

app.py – delete_entry() Python + SQL 
connection.execute("DELETE FROM entries WHERE id = ?", (entry_id,))
connection.commit()
03

Das Tagesziel in settings speichern

Das Tagesziel wird nie neu eingefügt, sondern nur geändert – es steht ja schon die eine Zeile mit id = 1 da. Zusätzlich wird goal_set auf 1 gesetzt: die App merkt sich so, dass das Ziel nun bewusst gewählt wurde und das Start-Formular nicht mehr nötig ist.

app.py – update_goal() Python + SQL 
connection.execute(
    "UPDATE settings SET daily_goal = ?, goal_set = 1 WHERE id = 1",
    (2200,),
)
04

Warum diese ?-Platzhalter?

Man könnte SQL-Text einfach zusammensetzen – aus "..." + name + "...". Das ist aber gefährlich: eine Attacke namens . Wer statt eines Namens ' ; DROP TABLE entries; -- eingibt, hängt seinen Befehl hinten an, und die Tabelle ist weg. Mit Platzhaltern behandelt SQLite die Eingabe konsequent als reine Daten – sie kann nie als SQL-Befehl ausgeführt werden.

Unsicher – so macht man es nicht Python 
# name kommt direkt aus dem Formular!
sql = "SELECT * FROM entries " \
      "WHERE name = '" + name + "'"
connection.execute(sql)
Sicher – so wie in app.py Python 
# Der Wert wandert getrennt vom SQL-Text:
connection.execute(
    "SELECT * FROM entries WHERE name = ?",
    (name,),
)
KAPITEL 05

Warum sieht der Code so aus, wie er aussieht?

Die typischen Fragen mit Begründung – falls im Kolloquium danach gefragt wird.

Warum zwei Tabellen statt einer großen?

Das Tagesziel ändert sich höchstens alle paar Wochen, Mahlzeiten mehrmals täglich. Würde daily_goal in jeder Mahlzeitenzeile mitstehen, müsste man bei jeder Änderung alle Zeilen anpassen – und alte Einträge würden rückwirkend „umgeschrieben“. In settings steht das Ziel genau einmal.

Warum Datumsangaben als TEXT?

Das Format JJJJ-MM-TT (z. B. 2026-10-22) sortiert sich von selbst chronologisch: „2026-10-22“ steht vor „2026-11-01“, obwohl das Wort „Oktober“ alphabetisch nach „November“ käme. Auch WHERE date = ? funktioniert damit ohne weitere Tricks.

Warum calories mit speichern, obwohl es berechenbar ist?

Man könnte die Kalorien jederzeit aus Wert und Menge neu berechnen. Das wird aber ständig gebraucht: Der Kalender und das Dashboard addieren SUM(calories) über ganze Monate. Eine fertig berechnete Spalte lässt sich direkt summieren, das Ergebnis ist außerdem immer gleich – auch wenn später jemand die Rechenlogik ändert.

Warum CREATE TABLE IF NOT EXISTS?

init_database() läuft bei jedem Programmstart. Der Zusatz sorgt dafür, dass Tabellen nur angelegt werden, wenn sie fehlen. Ein Neustart löscht also niemals bestehende Einträge – erst das manuelle Löschen der Datei database.db setzt die App zurück.

Warum erst connection.commit()?

execute() führt einen Befehl nur aus – die Änderung liegt zunächst in einer Art Zwischenspeicher. Erst commit() schreibt sie in die Datei database.db. Ohne diesen Aufruf wäre die Änderung nach dem Schließen weg.

Warum row_factory = sqlite3.Row?

Standardmäßig liefert SQLite wie ('Apfel', 52.0), also nur Werte in Reihenfolge. Mit Row kann das Ergebnis über den Spaltennamen angesprochen werden: zeile["name"] – lesbarer und unanfällig, wenn sich mal die Spaltenreihenfolge ändert.

KAPITEL 06

Häufige Fragen

Was passiert, wenn ich database.db lösche?

Beim nächsten Start legt init_database() die Datei mit beiden leeren Tabellen neu an und trägt eine Startzeile in settings ein (Ziel 2000 kcal, goal_set = 0). Das heißt: Es erscheint wieder das Einrichtungs-Formular, alle Mahlzeiten sind weg. Die Datei ist also der komplette Datenbestand – es gibt kein zweites Backup.

Kann ich mir die Datenbank selbst ansehen?

Ja. Im Terminal, im Projektordner: sqlite3 database.db, danach z. B. SELECT * FROM entries; oder .schema für den Aufbau. Änderungen sollten dort allerdings nicht von Hand gemacht werden – dafür ist die App da.

Warum SQLite und keine „echte“ Datenbank wie MySQL?

MySQL oder PostgreSQL brauchen einen eigenen Server, der installiert, gestartet und mit Benutzern und Passwörtern eingerichtet werden muss. Für eine App mit einer Nutzerin und lokal gespeicherten Daten wäre das Overhead. SQLite erledigt dasselbe (echtes SQL, feste Spaltentypen, sichere Zugriffe) – nur als Datei und ohne Adminkram.

Liegt die Datenbank im Internet?

Lokal nein – database.db liegt nur auf deinem Rechner. Auf dem Hosting (Render) liegt sie im Arbeitsordner des Servers und gehört ausschließlich dieser App; andere Seiten haben keinen Zugriff darauf. Ein Zugang per Benutzername/Passwort ist nicht nötig, weil SQLite keine Netzwerk-Schnittstelle hat.

Können zwei Personen gleichzeitig eintragen?

Solange es nur ein oder zwei Einträge pro Minute sind: ja. SQLite sperrt die Datei kurz beim Schreiben. Für echten Mehrbenutzer-Betrieb mit vielen gleichzeitigen Schreibvorgängen bräuchte es einen Server-Datenbank wie MySQL – der Punkt ist hier aber bewusst nicht erreicht.

Kurz zusammengefasst: Jede Mahlzeit ist eine Zeile in entries, dein Tagesziel steht als einzelne Zeile in settings. Der Python-Code greift immer über die vier Befehle SELECT, INSERT, UPDATE und DELETE auf die Tabellen zu – dabei ausschließlich mit ?-Platzhaltern, damit Benutzereingaben niemals als SQL ausgeführt werden können.
